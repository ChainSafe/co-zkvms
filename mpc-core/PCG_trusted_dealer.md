# Plan: BarnOwl-compatible edaBits via dealer-seeded EA‑LPN PCG (Rep3)

## 0) Goal & success criteria

**Goal:** Replace the current nonstandard “Cheng’23 online phase” (`{[[v]]^A, γ, θ}` shape) with a **BarnOwl-compatible** preprocessing + online B2A that consumes **standard daBits/edaBits** correlations, generated lazily via a **PCG expander (EA‑LPN)** with **P0 as a trusted dealer**.

**Success criteria:**
- New module `mpc-core/src/protocols/rep3_ring/edabits_pcg.rs` exists and is used by `co-jolt2`.
- No raw edaBits are stored in memory (no `Vec<EdaBits>`-style caches sized to trace length).
- `take_edabits_u64()` (and other widths used by co-jolt2) expands **on demand** using an efficient expander path (EA‑LPN), not per-element slow parsing.
- B2A conversion works for packed Rep3 XOR-shares and matches plaintext semantics.
- Unit tests in `mpc-core` + integration test `cargo test -p co-jolt2 dag_correct` pass.

## 1) What’s missing / underspecified in BarnOwl.pdf

BarnOwl is a good “what” but incomplete for our “how” in this setting:
1) **edaBit construction details:** The paper explicitly says their baseline semi-honest edaBit generation is a *naive combination of daBits* and does **not** give a crisp step-by-step algorithm for our exact representation choices (packed XOR-share `Rep3RingShare<T>` + field share `Rep3PrimeFieldShare<F>`).
2) **PCG parameterization:** Boyle22 gives EA-code families and security discussion, but choosing concrete `(n, N, density/weight, field/ring)` parameters for our throughput/latency target is not “drop-in”.
3) **Silent-OT plumbing:** BarnOwl’s full silent OT/COT pipeline (Appendix B / Fig 10–11) relies on PPRFs/DPFs and details delegated to prior work. We are *explicitly not implementing that stack*; instead we use a dealer model and EA‑LPN expander as the only “heavy” piece.

### 3.3 Trusted-dealer model for base correlations
Because we cannot compress arbitrary correlated outputs, we use **structured correlations** generated by a PCG:
- P0 (dealer) runs a short setup once and distributes compact seeds/hints to P1/P2.
- Thereafter each party locally expands the seeds into a long stream of daBit/edaBit material.

Concretely, pool initialization will:
- fork a dedicated RNG stream from `IoContextPool` (so all parties stay aligned deterministically)
- run a **dealer setup phase** where P0 sends:
  - expander seeds + any small fixed “public matrices/params IDs”
  - per-stream correction “hints” required by the EA‑LPN correlation
P1/P2 receive and store only these seeds/hints.

This satisfies the user constraint “avoid complicated OT by using P0 as trusted dealer” while still giving an LPN/PCG-style expander.

## 4) EA‑LPN expander implementation (Boyle22-style)

### 4.1 Implementation scope (what we implement)
Implement only the **EA code expander** mechanics from Boyle22 needed for fast stretch:
- accumulator `A` (prefix sums)
- sparse expander/replication step `B`
- streaming multiply `H = B·A` applied to a sparse/noisy input

We will implement it as a deterministic “generator” that can:
- expand seeds into a pseudorandom vector stream over:
  - `F2` (bits) and/or
  - `Fp` (field elements)
depending on which correlations we need for daBits/edaBits.

### 4.2 Parameters & defaults (decision complete)
Choose a conservative initial parameter set intended for correctness/perf, not paper-tight security:
- security target: 128-bit computational (documented as “engineering default”)
- expand factor: sized so that `take_edabits_u64()` can serve at least “trace-length scale” calls without reseeding
- density/weight: small constant (e.g., 3–5) for sparse replication; accumulator always enabled
- matrix is **implicit** (no materialized `n×N`)

## 5) How the PCG produces daBits/edaBits in our representation


### 5.2 Construction approach (dealer-seeded)
We implement a BarnOwl-inspired dealer distribution:
- Use EA‑LPN PCG to generate a long stream of OT-like “selectable” masks enabling parties to locally derive field shares consistent with the XOR-bit without interactive bit-injection.
- Because P0 is trusted, we do not implement PPRF/DPF; P0 provides the base “seed OT” correlation for the EA‑LPN expander directly.


## 9) Explicit assumptions & non-goals

Assumptions (documented in code):
- **P0 is trusted** for this preprocessing (dealer can choose and know seeds/correlations).
- Semi-honest setting; no malicious cut-and-choose verification is implemented in this milestone.

Non-goals (this milestone):
- Implementing BarnOwl Appendix B silent OT/PPRF/DPF stack.
- Achieving paper-tight LPN security reductions/parameters on first pass.
- Optimizing for WAN/benchmarking; we will add benchmarks after correctness.
